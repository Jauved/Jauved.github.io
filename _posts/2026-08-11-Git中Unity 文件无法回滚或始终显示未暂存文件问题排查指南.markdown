# Git 中 Unity 文件无法回滚或始终显示未暂存文件问题排查指南

> 适用场景: SourceTree 持续显示文件 Modified, 点击丢弃/恢复后又出现, 或 Diff 看不到实际改动.
>
> **阅读顺序:** 先看 W 解决问题; 需要理解命令或长期维护 `.gitattributes` 时再看 I; 特殊文件类型、嵌套仓库及其他异常看 S.

## W - 直接使用

### W1. 最常用修复命令

**如果已经确认是换行符或 `.gitattributes` 规范化问题**, 在对应 Git 仓库内执行:

```bash
git add --renormalize -- "Path/File.meta"
```

这会让 Git 使用当前 `.gitattributes` 等规则重新处理**已跟踪文件**, 并更新 Index (暂存区). **它不是“丢弃修改”命令, 也不会自动提交.** 执行后需检查暂存内容.

### W2. 不确定原因时, 最快判断(基于PowerShell)

把下面的路径替换成 SourceTree 显示异常的文件, 路径相对于**当前仓库根目录**:

```bash
$p = "Path/File.cs"
git status --short -- "$p"
git ls-files --eol -- "$p"
```

| 结果                                                         | 应如何处理                                                   |
| ------------------------------------------------------------ | ------------------------------------------------------------ |
| `git status --short` **没有输出**                            | Git 已认为文件正常. 先刷新或**关闭并重新打开 SourceTree 仓库**, 不要重复修复文件. |
| `git status` 显示修改, 同时出现 `i/crlf ... attr/text eol=lf` | Index 仍是 CRLF, 当前规则要求 LF. 先看 W3 排除实际内容变化, 再尝试 W1. |
| `git status` 显示修改, 但 `i/lf w/lf attr/text eol=lf`       | 当前换行符匹配. **不能仅凭 EOL 结果判断文件无修改**, 应检查 Diff. |
| 出现 `i/-text` 或 `w/-text`                                  | Git 将相应内容识别为二进制. 先检查文件类型和 `.gitattributes`, 参见 S2. |

**只需先记住:** `i` = Index, `w` = Working Tree, `attr` = 当前属性规则. 具体解释放在 I1.

### W3. 确认后修复并验证

先查看未暂存和已暂存的变化:

```bash
git diff -- "$p"
git diff --cached -- "$p"
```

如果怀疑只有行尾差异, 再辅助检查:

```bash
git diff --ignore-space-at-eol -- "$p"
git diff --cached --ignore-space-at-eol -- "$p"
```

**判断:** 忽略行尾空白后没有 Diff, 说明差异可能主要来自行尾, 但不能单靠它证明所有内容一致. 有真实代码/资源修改时, 先保留或处理这些改动.

确认规范化规则正确后:

```bash
git add --renormalize -- "$p"
git status --short -- "$p"
git diff --cached -- "$p"
git ls-files --eol -- "$p"
```

- `git status` 没有输出: Git 已经认为文件正常; SourceTree 仍显示异常时重新打开仓库.
- 出现已暂存修改: 检查是否只是预期的规范化变化; **只有确实需要更新仓库基线时才提交**.
- 仍有不符合预期的内容变化: 不要反复执行 `renormalize`, 继续看 S.

### W4. 本次实际遇到的情况

检查文件时得到:

```text
i/lf    w/lf    attr/text eol=lf
```

并且 `git status --short`、`git diff` 都没有输出. **这只能证明当时命令行 Git 已认为文件干净**, 不能反推最初的问题一定是换行符.

后来重新打开 SourceTree 仓库, Modified 提示消失. 因此本次最后一步是**刷新 SourceTree 的显示状态**, 而不是再次修改 Index.

## I - 原理与常用配置

### I1. 问题现象与三个状态来源

Unity 工程中可能出现以下现象:

- SourceTree 一直显示某个文件为 Modified.
- 点击恢复后仍然出现.
- 暂存、恢复反复无效.
- Diff 看不到实际内容变化.
- `git restore` 后 `git status` 仍然显示修改.

一种常见原因是以下三者对文本/二进制或 CRLF/LF 的理解不一致:

```text
Git Index 中的文件状态
        +
Working Tree 中的实际文件
        +
.gitattributes 的规则
```

但也可能是普通内容修改或 SourceTree 显示状态未刷新, 因此必须以 `git status`、Diff 和属性输出综合判断.

#### `git ls-files --eol` 怎么看

```bash
git ls-files --eol -- "$p"
```

常见结果:

```text
i/lf    w/lf    attr/text eol=lf
i/crlf  w/crlf  attr/text eol=lf
i/-text w/-text attr/text=auto eol=lf
```

各字段含义:

| 字段       | 常见值                      | 意义                                                         |
| ---------- | --------------------------- | ------------------------------------------------------------ |
| `i/...`    | `i/lf`, `i/crlf`, `i/-text` | **Index (暂存区)** 中保存内容的换行符类型; `-text` 表示被识别为非文本内容. |
| `w/...`    | `w/lf`, `w/crlf`, `w/-text` | **Working Tree (工作区)** 中实际磁盘文件的换行符类型.        |
| `attr/...` | `attr/text eol=lf`          | 当前规则强制作为文本, 检出时使用 LF.                         |
| `attr/...` | `attr/text=auto eol=lf`     | 当前规则由 Git 判断文本或二进制; 判断为文本时采用 LF.        |
| `attr/...` | `attr/-text`                | 当前规则明确禁用文本换行符规范化.                            |

`i/lf w/lf attr/text eol=lf` 表示这几项**换行符信息匹配**, **不等于**文件一定没有真实改动.

#### 查看当前真正生效的 `.gitattributes`

```bash
git check-attr -a -- "$p"
```

例如:

```text
text: set
eol: lf
```

表示 Git 对这个路径启用了文本规范化, 并要求工作区使用 LF.

#### 区分两个 Diff

```bash
# 工作区与 Index (未暂存)
git diff -- "$p"

# Index 与 HEAD (已暂存)
git diff --cached -- "$p"
```

如果想过滤行尾空白差异, 分别加上 `--ignore-space-at-eol`. **该选项会忽略部分实际空白变化**, 因此应与普通 Diff 配合使用.

### I2. 为什么 `git add --renormalize` 有效

`git add --renormalize` 会按照**当前 Git 属性和 clean 规则**重新处理已被跟踪的文件, 再把结果写入 Index.

这适用于历史 Index 仍保存 CRLF, 但 `.gitattributes` 已经要求 LF 的情况. 也适用于修改 `text` 属性或 `core.autocrlf` 后重新规范化受影响文件.

它不直接把文件恢复为 `HEAD`, 不保证工作区内容被重写, 也不自动提交. 应检查 `git diff --cached` 的具体变化后, 再决定是否提交规范化结果.

### I3. 修改 `.gitattributes` 后如何让旧文件生效

**`.gitattributes` 改变以后, 已经被 Git 跟踪的文件不会自动全部重新应用新规则.**

仅处理某个文件 (优先推荐):

```bash
git add --renormalize -- "$p"
git status
```

如果这次还修改了 `.gitattributes` 文件本身, 需要一并暂存:

```bash
git add .gitattributes
```

确认没有问题后再提交.

如果已经确认**整个仓库**都需要统一规则, 才考虑批量处理:

```bash
git add --renormalize .
git status
git diff --cached --stat
```

**不要执行完直接提交.** 如果突然出现大量图片、FBX 或其他二进制资源修改, 先停止并检查 `.gitattributes`.

检查暂存区是否主要是行尾差异:

```bash
git diff --cached --ignore-space-at-eol
```

没有输出可以支持“主要是行尾空白差异”的判断, 但不能代替查看完整 Diff.

### I4. Unity 推荐的关键 `.gitattributes` 规则

这是原文保留的 Unity 规则示例. 请根据工程实际文件类型检查后使用, 而不是无条件覆盖现有配置:

```gitattributes
* text=auto

*.cs              text eol=lf diff=csharp
*.shader          text eol=lf
*.compute         text eol=lf
*.cginc           text eol=lf
*.hlsl            text eol=lf
*.shadergraph     text eol=lf
*.shadersubgraph  text eol=lf

*.meta            text eol=lf
*.unity           text eol=lf
*.prefab          text eol=lf
*.mat             text eol=lf

# .asset 可能是 Text 或 Binary.
*.asset           text=auto eol=lf

*.png binary
*.jpg binary
*.jpeg binary
*.dll binary
```

核心原则:

```text
明确是文本的 Unity 文件 -> text eol=lf
可能是文本或二进制      -> text=auto
明确是二进制            -> binary
```

其中, **`*.asset` 不一定是 YAML 文本**, 部分 Terrain 等资源可能使用二进制格式. 对于已知的二进制文件类型, 应明确关闭文本规范化; 对混合类型则按实际内容验证 `text=auto` 的判断结果.

### I5. `core.autocrlf` 的作用与检查

检查当前生效的配置以及来源:

```bash
git config --show-origin --get core.autocrlf
```

如果仓库已通过 `.gitattributes` 明确规定 `eol=lf`, 应优先按照仓库的 `.gitattributes` 统一规则.

必要时, 可以在**当前仓库**设置:

```bash
git config core.autocrlf false
```

这只是辅助配置, **不能替代 `.gitattributes`**, 也不应将随意切换 `core.autocrlf` 当作通用修复手段. 修改后是否需要 `renormalize`, 要根据实际文件和属性检查决定.

## S - 特殊情况与排错

### S1. Index 是 CRLF, 规则却要求 LF

典型结果:

```text
i/crlf  w/crlf  attr/text eol=lf
```

说明仓库 Index 中仍保存 CRLF, 当前规则已经要求 LF. **先确认 Diff 中没有需要保留的实际内容修改**, 再执行:

```bash
git add --renormalize -- "$p"
git status
git ls-files --eol -- "$p"
```

规范化成功时, Index 的 EOL 可能变为:

```text
i/lf ...
```

如果产生暂存修改, 确认内容无误后再正常提交; 不是所有情况下都一定需要提交.

### S2. Unity `.asset` 实际是 Binary, 却被当成 Text

Unity `.asset` 不一定是 YAML 文本, Terrain 等资源可能是二进制格式.

不建议对所有 `.asset` 一律强制文本:

```gitattributes
*.asset text eol=lf
```

对于混合类型的仓库, 可以考虑:

```gitattributes
*.asset text=auto eol=lf
```

Git 会尝试区分:

```text
YAML .asset    -> Text   -> LF
Binary .asset  -> Binary -> 不做换行转换
```

先修改 `.gitattributes`, 然后针对**确实受影响的文件**重新规范化:

```bash
$p = "Path/File.asset"
git add .gitattributes
git add --renormalize -- "$p"
git status
```

再验证:

```bash
git check-attr -a -- "$p"
git ls-files --eol -- "$p"
```

二进制 `.asset` 的正常结果可能是:

```text
i/-text w/-text attr/text=auto eol=lf
```

`text=auto` 仍需要在真实资源上验证. 对明确已知的二进制资源, 可以单独配置为 `binary` 或 `-text`.

### S3. 文件本来就有真实内容修改

如果 Diff 中确实存在 C# 代码或 Unity 数据的修改, 它就不应仅按 EOL 问题处理.

**只有你明确要丢弃该文件的已暂存及未暂存修改时**, 才执行:

```bash
git restore --source=HEAD --staged --worktree -- "Path/File"
```

**警告:** 该命令会覆盖指定文件的本地改动. 不能把它当作规范化操作, 也不要在尚未确认内容时执行.

### S4. 嵌套 Git 仓库需要额外注意

Unity 项目可能存在独立维护的 Git Package, 例如:

```text
Repository A
└── Packages/
    └── Repository B
```

如果 A 和 B **都实际跟踪同一个物理文件**, 那么该文件可能分别受到:

```text
Repository A 的 Index / .gitattributes
Repository B 的 Index / .gitattributes
```

两套规则影响. 因此可能出现子仓库已规范化为 LF, 但父仓库的 Index 仍保存 CRLF 的情况.

首先分别在两个仓库的终端中确认仓库根目录:

```bash
git rev-parse --show-toplevel
git rev-parse --git-dir
```

再分别检查**同一物理文件在对应仓库中的相对路径**:

```bash
git status --short -- "文件相对路径"
git ls-files --eol -- "文件相对路径"
git check-attr -a -- "文件相对路径"
```

确定真正出现问题的仓库之后, **只在该仓库**对相应文件运行 `git add --renormalize`.

补充: 标准 Git submodule 的父仓库一般只跟踪子模块引用 (gitlink), 并不跟踪子模块内的每一个文件. 只有父仓库确实同时跟踪对应文件时, 才存在上述双重 Index 问题. 如果 `git ls-files --eol` 没有返回该文件, 先检查路径和仓库归属, 不要强行处理.

### S5. Git 状态干净, SourceTree 却仍显示 Modified

先检查:

```bash
git status --short -- "Path/File"
git ls-files --eol -- "Path/File"
```

如果 `git status --short` 没有输出, Git 已认为该文件正常. 这时应先刷新 SourceTree; 如果没有改善, 关闭并重新打开仓库.

**本次已验证:** 终端中 `i/lf w/lf attr/text eol=lf`, `git status` 无修改, 重新打开 SourceTree 后 UI 恢复正常. 此现象不应再次用 `renormalize` 或 `reset --hard` 处理.

如果重开后仍不一致, 对比终端与 SourceTree 所打开的仓库路径, 并检查 SourceTree 使用的是 Embedded Git 还是 System Git.

### S6. 不建议的处理方式

不要用下面的命令隐藏问题:

```bash
git update-index --assume-unchanged "文件"
```

也不要一开始就执行可能丢失本地修改的命令:

```bash
git reset --hard HEAD
```

更不要在大型旧 Unity 项目中未经检查就全仓库规范化:

```bash
git add --renormalize .
```

推荐的排查顺序始终是:

```text
定位异常文件
    ↓
确认当前 Git 仓库
    ↓
检查 git status 与 i / w / attr
    ↓
检查普通 Diff / 行尾差异
    ↓
必要时修正 .gitattributes
    ↓
小范围 git add --renormalize
    ↓
检查暂存 Diff / git status
    ↓
按需要提交; 如果 Git 已干净但 UI 异常, 刷新或重开 SourceTree
```
